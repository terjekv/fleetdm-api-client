# Architecture

The crate has two API layers sharing one authenticated transport:

1. Curated endpoints provide ergonomic methods, validation, and typed models.
2. Generated raw wrappers provide transport access to every route recognized in
   the pinned Fleet documentation.

Both layers use the same URL construction, authentication, retry, response-size,
and error-mapping behavior.

## Client and authentication

`src/client.rs` owns `FleetClientBuilder<State>` and `FleetClient`. The builder
starts as `FleetClientBuilder<Unauthenticated>` and exposes `build()` only after
`login()` or `with_token()` returns `FleetClientBuilder<Authenticated>`.

Public authentication operations that intentionally require no token are
available from the unauthenticated builder. All other endpoint accessors live on
the authenticated `FleetClient`.

The built-in `reqwest::Client` uses a 30-second timeout, Rustls through the
selected `reqwest` feature set, and a no-redirect policy. Supplying a custom
client transfers responsibility for those settings to the caller.

## Shared HTTP transport

`src/http/` owns:

- request sending and rebuildable multipart requests;
- HTTP 429 retry integration;
- typed response decoding;
- Fleet error response parsing and status mapping;
- query encoding and path-segment helpers;
- response-size enforcement;
- bounded file responses and streaming package responses.

Endpoint modules should not call `reqwest::Client` directly or duplicate status
handling. Mutations whose successful body has no semantic value use the shared
empty-response path so Fleet version differences between empty and informational
success bodies remain compatible.

## Curated endpoints and models

`src/endpoints/<area>.rs` contains endpoint behavior. `src/models/<area>.rs`
contains request, response, and domain wire types. `src/paths.rs` is the central
source for curated API paths.

Request models expose fields when callers are expected to construct them.
Response models generally keep fields private and expose narrow accessors. Open
Fleet payloads use `serde_json::Value` deliberately; stable curated contracts use
typed models.

Known invalid state is rejected before a request is sent. Examples include empty
identifiers, no-op updates, mutually exclusive label targeting, unsafe upload
filenames, and invalid certificate-authority configuration.

## Generated raw API

`src/endpoints/raw_api.rs` is generated by `scripts/update-spec-api.py` from
`docs/fleet-rest-api-main.md`. Do not edit it manually.

Each wrapper is derived from an HTTP method and documented path. Dynamic path
segments are encoded, and successful responses retain their HTTP status, headers,
and bounded bytes in `ApiResponse`. JSON decoding is lazy.

Generated coverage is intentionally syntactic. The generator cannot infer every
Fleet payload invariant or edition-specific behavior from Markdown.

## Adding a curated endpoint

A normal endpoint addition includes:

1. A constant or builder in `src/paths.rs`.
2. Request and response types in the matching model module.
3. Validation close to the request data.
4. An endpoint method using the shared HTTP helpers.
5. Module exports and a `FleetClient` accessor when adding a new area.
6. Focused offline tests asserting method, encoded URL, payload, result, and
   error behavior.
7. Rustdoc, an example, or README coverage when callers need usage guidance.
8. A changelog entry for user-visible behavior.

If the Fleet documentation or generator changes, regenerate the raw API and run
the route coverage check.

## Compatibility strategy

Public methods, exported types, serialized names, and features are treated as
compatibility commitments. Fleet wire variants supported by observed responses
use explicit aliases, optional fields, defaults, or narrowly flattened maps.

The project is still in `0.0.x`; breaking changes can occur, but they should be
intentional and recorded in the changelog. Security fixes take priority over
preserving unsafe behavior.

## Verification layers

- Unit tests cover model, validation, encoding, retry, and redaction behavior.
- Offline integration tests use a mock HTTP server to verify complete request and
  response contracts deterministically.
- Route coverage tests compare generated wrappers with the pinned spec.
- Examples compile as test targets.
- Documentation examples compile through rustdoc.
- The opt-in live suite exercises a disposable Fleet preview.
- CI checks the MSRV, stable Rust, Clippy, formatting, generated drift, and
  dependency advisories.
